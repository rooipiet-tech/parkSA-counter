statement: A test that transforms data with the same operation it then asserts is tautological and makes the spec clause it 'covers' vacuous. Ordering/monotonicity checks are the classic trap: sorting rows by device_ts and then asserting they are sorted proves nothing. Assert the transformed output against an independently recorded ground truth (e.g. the tap order the queue recorded at enqueue time), not against a re-derivation of the same field.
evidence: OR-F2 major: offline-50.spec.ts sorted events by device_ts then asserted sorted order; AC-07 offline ordering was effectively untested. OR-F6: a fixture generated by the same code under test is a regression pin, not a correctness proof.
catch_next_time: Review lens for self-referential assertions: reject any assert whose expected value is computed by the same function/sort/transform being verified. Require at least one independently-derived or hand-computed expected value per aggregation/ordering criterion.
