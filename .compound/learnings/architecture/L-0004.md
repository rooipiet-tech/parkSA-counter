statement: In an offline sync queue, deleting a pending row by key after the server acks it is a lost-update race: if the row was mutated between read and delete (e.g. a session upsert acks while endSession writes end_ts to the same pending row), the delete discards the newer unsent mutation and the change never reaches the server. Use compare-and-delete (delete only if the row is unchanged from what was flushed) or re-read-and-re-enqueue the delta.
evidence: OR-F1 major: doFlush deleted pendingSessions by key after upsertSession ack; endSession racing the in-flight upsert had its end_ts/end_source row deleted unsent, leaving the server session open forever. OR-F5: undo racing a flush ack could persist stale synced:false in IDB.
catch_next_time: For every queue drain, require delete/ack to be conditional on unchanged-since-read, and add a unit test that mutates a pending row while its flush is in flight, then asserts the mutation still reaches the backend.
