statement: Destructive developer/test escape hatches (query-param or global that clears storage/DB, seeds, or resets state) must be gated behind a DEV/build flag and must never run in the production bundle — and even in dev should refuse to wipe when unsynced/unrecoverable data is present. A convenience reset hook shipped live directly contradicts a zero-data-loss guarantee, and it won't surface in normal testing because tests intentionally invoke it.
evidence: RS-02 major: ?fresh=1 boot hook was active in production, clearing localStorage and deleting IndexedDB including unsynced pendingEvents with no confirmation, violating the zero-loss spirit of the offline queue.
catch_next_time: Scan the production build for reset/seed/wipe hooks reachable via URL params or globals; require DEV gating and a 'refuse if pending data' guard. Add a test asserting the hook is inert in a prod build.
